Admin Panel Security

CRITICAL

Layer 1 — Return 404, Not 401

Never confirm the admin panel exists to an unauthenticated visitor. 401/403 tells an attacker "this route exists, keep trying." 404 tells them nothing.

middleware.ts
// ✗ WRONG — confirms admin exists return NextResponse.json({ error: 'Unauthorized' }, { status: 401 }) // ✓ CORRECT — admin panel is invisible to attackers if (!isValidAdminJWT(request)) { return NextResponse.notFound() // returns 404 }

Layer 2 — IP Allowlist (Most Effective)

Only your IP and your staff's IPs can reach /admin. Someone in Germany who finds the URL gets a 404 regardless of credentials. Update the list when staff join or their IP changes.

middleware.ts — IP allowlist
const ADMIN_ALLOWED_IPS = [ process.env.OWNER_IP, // Your home/office IP process.env.STAFF_IP_1, // Staff member 1 process.env.STAFF_IP_2, // Staff member 2 (add as team grows) ] export function middleware(request: NextRequest) { if (request.nextUrl.pathname.startsWith('/admin')) { const ip = request.headers.get('x-forwarded-for')?.split(',')[0].trim() // Step 1: IP check first (cheapest check) if (!ADMIN_ALLOWED_IPS.includes(ip)) { return NextResponse.notFound() // Not even a login page shown } // Step 2: JWT check const token = request.cookies.get('admin_token')?.value if (!isValidAdminJWT(token)) { return NextResponse.notFound() } } }
⚠
Dynamic IP Problem If your home internet has a dynamic IP (changes on router restart), store IPs in environment variables and update them when they change. Alternatively, use a VPN with a fixed exit IP — all admin access goes through VPN.

Layer 3 — Admin-Only Phone Numbers

.env
ADMIN_PHONE_NUMBERS="+919876543210,+919876543211" # Only these numbers can ever receive an admin OTP # No UI to "register as admin" — hardcoded in env always
lib/auth/neon-auth.ts
const adminPhones = process.env.ADMIN_PHONE_NUMBERS?.split(',') ?? [] export async function verifyAdminOTP(phone: string, otp: string) { if (!adminPhones.includes(phone)) { return { error: 'not_found' } // 404 behaviour, no info leak } // proceed with OTP verification... }

Layer 4 — OTP Rate Limiting

lib/auth/rate-limit.ts — Upstash Redis
// 5 failed OTP attempts → lock phone for 30 minutes // Prevents brute-force OTP guessing const key = `otp:attempts:${phone}` const attempts = await redis.incr(key) if (attempts === 1) await redis.expire(key, 1800) // 30 min TTL if (attempts > 5) { return { error: 'too_many_attempts', retry_after: '30 minutes' } }

Layer 5 — Admin Session Security

01

Short session expiry for admin

Customer JWT expires in 7 days. Admin JWT expires in 8 hours. Admin session ends at end of workday, always.

02

HttpOnly + Secure + SameSite cookie

Admin token stored as httpOnly cookie. JavaScript on the page cannot read it. XSS attacks cannot steal it.

03

Session invalidation on logout

Store a session_id in admin_sessions table. On logout, delete the row. JWT is now invalid even if someone stole the token before expiry.

04

No "remember me" for admin

Customers can have persistent sessions. Admin never. Every new browser session requires fresh OTP. Non-negotiable.

🛑
Summary: 4 layers protect admin panel IP allowlist → 404 on fail → OTP to approved phone only → Rate limit attempts → 8h JWT with server-side invalidation. An attacker needs to bypass ALL four. That is practically impossible without physical access to your phone and network.

Backend API Security

CRITICAL

Route-Level Authorization

Every API route must follow this pattern
// 3-check pattern for every protected route export async function POST(request: NextRequest) { // 1. Is user authenticated? const user = await getAuthUser(request) if (!user) return NextResponse.json({ error: 'not_found' }, { status: 404 }) // 2. Does user have permission for THIS action? if (user.role !== 'admin') return NextResponse.json({ error: 'not_found' }, { status: 404 }) // 3. Does user own THIS resource? (for user-scoped actions) if (order.userId !== user.id) return NextResponse.json({ error: 'not_found' }, { status: 404 }) // Safe to proceed }

Input Validation — Zod on Every Route

features/orders/schema.ts
// Validate and sanitize ALL incoming data — never trust client input const CreateOrderSchema = z.object({ productId: z.string().uuid(), qty: z.number().int().min(1).max(100), addressId: z.string().uuid(), // Never accept price from client — always read from DB }) // In route handler: const result = CreateOrderSchema.safeParse(await request.json()) if (!result.success) return NextResponse.json({ error: 'invalid_input' }, { status: 400 })
🛑
Never Accept Price from Client Never let the client send the price. Always read price from the database. A customer who sends price: 1 in the request body should not get a sofa for ₹1. This is the most common e-commerce attack.

Auth + JWT Security

CRITICAL

JWT Best Practices

01

Strong secret — minimum 256-bit random

Generate with: openssl rand -hex 32. Store in Vercel env vars. Never in code. Never in git. Rotate every 90 days.

02

Minimal payload — no sensitive data in JWT

JWT payload: { sub: userId, role, phone, iat, exp }. Never put full name, email, address, order history in the token. JWT body is base64 — readable by anyone.

03

Different expiry for customer vs admin

Customer JWT: exp: 7d. Admin JWT: exp: 8h. Admin sessions are always short.

04

Server-side session tracking for admin

Store session_id in JWT + in admin_sessions DB table. Validate both on each request. Logout = delete DB row = instant invalidation across all devices.

05

Verify algorithm explicitly

Always set algorithms: ['HS256'] in JWT verify. The "alg: none" attack is real — never let the library accept any algorithm.

Token Storage — Web vs Flutter

ClientWhere to StoreWhy
Web (Next.js)httpOnly; Secure; SameSite=Strict cookieJS on page cannot read it. XSS cannot steal it. Browser sends it automatically.
Flutter Appflutter_secure_storage (iOS Keychain / Android Keystore)OS-level encryption. Not accessible to other apps. Not in SharedPreferences (plaintext).
NeverlocalStorage, sessionStorage, SharedPreferencesPlaintext storage. XSS or any other app can read it. Token theft = account takeover.

Web Frontend Security

HIGH

XSS Prevention

01

Never use dangerouslySetInnerHTML with user data

Product descriptions, user names, review text — all must go through React's default JSX rendering which escapes HTML automatically. If you must render HTML (e.g. rich descriptions), use a sanitizer like DOMPurify first.

02

Sanitize all user-generated content before display

Any text that a user typed and is shown to other users (reviews, community posts, referral names) must be sanitized. npm install dompurify for client-side, sanitize-html for server-side.

03

Content Security Policy header

CSP header (see Backend section) tells the browser which scripts and sources are allowed to run. Stops injected scripts even if XSS gets through.

Form Security

CSRF Protection

  • Next.js Server Actions have built-in CSRF protection
  • For API routes: SameSite=Strict cookie blocks cross-site requests
  • Add Origin header check on state-changing routes
  • Never use GET requests for state-changing actions

Input Length Limits

  • Phone: exactly 10 digits (after +91 strip)
  • Name: max 100 chars
  • Address: max 500 chars
  • Any text field: set maxLength on input AND validate on backend

Sensitive Data — Never in Frontend

DataRule
Razorpay Key SecretBackend only. Frontend uses only the public Razorpay Key ID.
WhatsApp API tokenBackend only. Never in page source, never in JS bundle.
Anthropic API keyBackend only. AI calls made server-side always.
Other users' dataAPI routes must only return data for the authenticated user. Never expose other users' phone, email, or order data.
Admin routes/logicAdmin UI components must be in separate files. Never ship admin UI code in the customer bundle.

Flutter App Security

HIGH
🛑
Core Rule: The Flutter App is Untrusted. Anyone can decompile an APK in minutes. Assume every string, every URL, every key inside the app binary is public. Never put anything secret in the app. All secrets live on the backend.

Token Storage

pubspec.yaml + usage
dependencies: flutter_secure_storage: ^9.0.0 # iOS Keychain / Android Keystore // Store JWT after login final storage = FlutterSecureStorage() await storage.write(key: 'auth_token', value: jwt) // Read JWT for API calls final token = await storage.read(key: 'auth_token') // ✗ NEVER do this SharedPreferences.setString('auth_token', jwt) // Plaintext!

Network Security

01

Certificate Pinning

Pin your API domain's SSL certificate in the Flutter app. Prevents man-in-the-middle attacks on public WiFi. Use http_certificate_pinning package. Store the certificate hash, not the certificate itself.

02

HTTPS only — no HTTP fallback

In AndroidManifest.xml: android:usesCleartextTraffic="false". In iOS info.plist: disable NSAllowsArbitraryLoads. App must reject any HTTP connection.

03

API base URL from environment, not hardcoded

Use --dart-define=API_URL=https://alvari.com at build time. Not hardcoded in source. Makes it easy to switch environments (staging vs production) without code changes.

App Hardening

Android

  • Enable ProGuard / R8 code obfuscation
  • Set debuggable: false in release build
  • Disable backup: android:allowBackup="false"
  • Root detection: block app on rooted devices (optional)

iOS

  • Enable Bitcode for obfuscation
  • Set release scheme, not debug
  • No sensitive data in NSLog (stripped in release)
  • Jailbreak detection: block on jailbroken devices (optional)

Database Security

CRITICAL

Connection Security

01

Use Neon's pooled connection string

Neon provides two connection strings: direct and pooled (via PgBouncer). Always use the pooled one in your app. Prevents connection limit exhaustion with serverless functions — the most common Neon scaling issue.

02

One connection string per environment

Separate Neon branches: main (production), dev (local development), staging (if needed). The production connection string never goes into a dev machine's environment. Never.

03

Principle of least privilege

Create a dedicated DB user for the app with only SELECT, INSERT, UPDATE, DELETE permissions. No DROP, no CREATE TABLE, no schema changes. Migrations run with a separate admin user, never the app user.

SQL Injection Prevention

Always use Drizzle ORM — never raw string SQL with user input
// ✗ NEVER — SQL injection vulnerability db.execute(`SELECT * FROM products WHERE name = '${userInput}'`) // ✓ CORRECT — Drizzle parameterizes automatically db.select().from(products).where(eq(products.name, userInput)) // If raw SQL is ever needed (it shouldn't be), use parameterized queries: db.execute(sql`SELECT * FROM products WHERE name = ${userInput}`)

Sensitive Data at Rest

ColumnHow to Store
Phone numbersPlain (it's a contact field). Index it. It's not a secret.
OTP codesStore as hash only (bcrypt). Never store plain OTP. Compare hash on verify.
Admin session tokensStore as SHA-256 hash only. Token itself only lives in the cookie.
Razorpay payment IDsPlain — they are public transaction IDs, not secrets.
Customer addressesPlain — needed for delivery. Neon encrypts disk at rest by default.
PasswordsNot applicable — you use WhatsApp OTP, no passwords. Keep it this way.

Backups

ℹ
Neon handles backups automatically — point-in-time restore for 7 days on free tier, 30 days on paid. Enable the paid plan before you have real orders. Additionally, set up a weekly pg_dump export to an S3 bucket or Google Drive as a secondary backup. Test a restore every month.

The Rules

01

Never commit secrets to git

Add .env.local, .env.production, .env to .gitignore immediately. If you ever accidentally push a secret, rotate it within minutes — assume it was already scraped by bots.

02

Separate env per environment

Vercel has Production, Preview, and Development environments. Production secrets only go in Production. Development uses test keys (Razorpay test mode, Neon dev branch) — never real keys locally.

03

Scope secrets to the function that needs them

Don't dump every secret in one config.ts file. Import process.env.RAZORPAY_KEY_SECRET only inside lib/payments/. If a file doesn't need a secret, it shouldn't import it.

04

Add secret scanning to your repo

Enable GitHub's secret scanning (free, automatic). It will alert you if you accidentally commit an API key, connection string, or token. Also install the gitleaks pre-commit hook locally.

🛑
If a Secret Leaks — Act in 5 Minutes 1. Rotate the leaked key immediately (generate new key in Razorpay/Meta/etc). 2. Update Vercel env var. 3. Redeploy. 4. Check logs for unauthorized usage. Bots scan GitHub commits in under 2 minutes — speed matters.

WhatsApp API Security

HIGH

Webhook Verification — First Thing in Handler

app/api/v1/wa/webhook/route.ts
// Meta signs every webhook with HMAC-SHA256 // Verify BEFORE processing anything export async function POST(request: NextRequest) { const body = await request.text() const signature = request.headers.get('x-hub-signature-256') const expectedSig = 'sha256=' + createHmac('sha256', process.env.WA_APP_SECRET!) .update(body).digest('hex') if (signature !== expectedSig) { return NextResponse.json({ error: 'invalid_signature' }, { status: 401 }) } // Now safe to process the webhook payload const data = JSON.parse(body) // ... }

Compliance Rules (Meta can ban your number)

01

Check opted_in_whatsapp before every send

Every outgoing message — template or free-form — must check user.opted_in_whatsapp === true. One unsolicited message complaint can get your WhatsApp Business number permanently banned.

02

Only approved templates outside 24h window

Meta allows free-form messages only within 24h of the user's last message. After that, only pre-approved templates. Store last_user_message_at on each lead to enforce this automatically.

03

Rate limit outgoing messages per user

Max 1 template message per user per 24h for marketing category. Use Upstash Redis to track: wa:sent:{userId}:{date}. Automated broadcasts must respect this or trigger spam reports.

Payments Security

CRITICAL

The Payment Security Rules

01

Verify Razorpay webhook HMAC before touching any order

Razorpay signs every payment webhook. Verify the signature using RAZORPAY_KEY_SECRET before updating any order status. An attacker can send a fake "payment success" webhook — HMAC verification is the only protection.

02

Never accept price from client

The order amount is calculated on the backend from the DB price. Frontend sends productId + qty. Backend calculates total. Razorpay order is created with the backend-calculated amount. A ₹1 exploit is impossible this way.

03

Idempotency — handle duplicate webhooks

Razorpay may send the same webhook multiple times. Use razorpay_payment_id as a deduplication key. Before updating an order: check if payments table already has this payment ID. If yes, skip processing.

04

Razorpay Key ID vs Key Secret

RAZORPAY_KEY_ID is public — it goes in the frontend checkout. RAZORPAY_KEY_SECRET is private — it never leaves the backend. Never confuse the two.

05

Log all payment events

Every webhook received, every status change, every refund — logged with timestamp, payment ID, amount. Required for dispute resolution. Razorpay also keeps their own logs but you need your own record.

Staff Access Management

MEDIUM

How to Onboard a New Staff Member

01 → Add their phone number to ADMIN_PHONE_NUMBERS env var in Vercel Redeploy after saving
02 → Add their office/home IP to ADMIN_ALLOWED_IPS env var They can only access from known IPs
03 → In DB: insert row in users with role: "staff" and their phone Role determines what they can see
04 → They login via WhatsApp OTP at alvari.com/admin No password to share or forget
05 → Brief them on the NEVER list below 5-min verbal walkthrough

How to Offboard Staff

01 → Remove their phone from ADMIN_PHONE_NUMBERS env var Instant — they can no longer receive admin OTP
02 → Remove their IP from ADMIN_ALLOWED_IPS Redeploy Vercel after saving both
03 → Delete all rows from admin_sessions for their user_id Invalidates any active sessions immediately
04 → Set users.role = 'inactive' for their record Keeps audit trail but disables access

Staff Security Rules (Brief Every New Hire)

01

Never share your OTP with anyone

Not even with the owner. OTP is personal. If someone asks for your OTP, it's a social engineering attack. Reject it immediately.

02

Never access admin on public WiFi

Cafes, airports, hotels — all public WiFi is untrusted. Admin access only from home, office, or mobile data. If travel is needed, use mobile hotspot.

03

Never export or screenshot customer data

Phone numbers, addresses, order history are private customer data. No screenshots to personal phones. No CSV exports to personal email. This is both a security rule and a legal requirement (IT Act 2000).

04

Lock screen when stepping away

Admin panel session is 8 hours. But lock your laptop when you step away. Someone walking past an unlocked admin panel is a real threat.
